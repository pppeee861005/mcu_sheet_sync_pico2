# 創客實戰心得：嵌入式系統的極簡哲學 —— 為什麼重開機 (Reset) 優於軟體返回選單？

> **執行環境**：MicroPython v1.2x  
> **核心主題**：MCU 系統架構簡化、記憶體零碎化 (Fragmentation) 與死當避坑實戰

## 💡 一句話總結心得

> **「MCU 程式架構宜簡化。使用軟體回主選單對系統負荷太重，不如簡單重開機切換就好！」**

在資源受限的單晶片微控制器 (MCU) 世界裡，**試圖用高階作業系統 (如 Windows/Android) 的多工軟體切換思維來撰寫 MicroPython，往往會落入記憶體崩潰的泥淖。**  
反觀讓系統「結束任務時直接重啟」，才是最優雅、最穩定、最符合嵌入式極客精神的工程解法。

## 🔍 為什麼「軟體跳回主選單」會讓 ESP32 負擔過重？

今天在實作「雙系統切換」與「回退主選單」時，我們遭遇到了子系統退出後再次發送 HTTPS 或進入另一系統時死當的現象。經深入分析，背後有三大硬核底層原因：

### 1. MicroPython GC 的非壓縮特性 (Non-compacting GC)
* MicroPython 的垃圾回收機制 (Garbage Collector) 採用 **Mark-and-Sweep (標記-清除)**。
* 它的特點是：**只清空釋放無用記憶體，但「不會搬移搬動」現有物件來拼湊大空間**。
* 經過「開機動畫 ➔ Wi-Fi 連線 ➔ 系統 1 運行 ➔ 退出選單 ➔ 系統 2 運行」後，RAM 雖然帳面上還有 80KB~100KB 的空閒量 (`gc.mem_free()`)，但實際上已經千瘡百孔，佈滿了極小的碎片。

### 2. TLS / HTTPS (mbedTLS) 的大塊連續記憶體需求
* 當 ESP32 進行 HTTPS 連線時，底層的加密模組 (mbedTLS) 需要申請 **數塊連續且完整的記憶體區塊（例如 4KB ~ 16KB）** 來存放 TLS 握手金鑰、憑證與緩衝區。
* 當 RAM 嚴重碎片化時，即使總剩餘空間足夠，**只要找不到連續的 8KB 空間，底層 TLS 握手就會瞬間阻塞卡死或噴出底層錯誤**，這就是為什麼在執行一段時間後突然卡在 `Syncing Sheet...` 的主因！

### 3. 底層驅動與 Socket 殘留狀態
* 短連線頻繁發起時，若遇到網路延遲，未及時完全關閉的 TCP Socket 或 Wi-Fi 內部狀態機容易出現 `0x0102` (Wifi Internal State Error) 或阻塞，增加系統複雜度。

## 🏆 重開機切換 (Hardware/Software Reset) 的三大優勢

面對上述挑戰，回歸「重開機切換」展現出無可比擬的優勢：

1. **記憶體 100% 徹底重生**：
   * 每次重開機，整個 RAM 堆疊從零初始化，**碎片化直接歸零**，永遠保有最平整、最大的連續記憶體給 TLS 握手使用。
2. **硬體與週邊狀態乾淨俐落**：
   * 所有的 I2C、Wi-Fi 驅動、Socket、計時器全部回歸乾淨的出廠預設，不用在 Python 程式碼裡費盡心思寫繁瑣的釋放、防漏、防卡死邏輯。
3. **架構極簡化，維護成本超低**：
   * 遵循 **KISS 原則 (Keep It Simple, Stupid)**。程式碼不需要處理多層巢狀跳轉或複雜的狀態機，每一個子系統獨立、專注、單純，執行完畢若要切換，直接 `machine.reset()` 或按板子上的 RST 鈕即可。

## 🌟 創客思維的昇華

這次的實戰讓我們領悟到：
* **寫 PC 程式是在「揮霍」資源**：記憶體動輒 16GB/32GB，有虛擬記憶體與記憶體重整，多層視窗與背景隨意開。
* **寫 MCU 程式是在「駕馭」極簡**：ESP32 只有幾百 KB 的 SRAM，**最好的架構不是把所有功能揉成一團大怪獸，而是讓每個模組小而美、任務結束即釋放。**

用最簡單的重開機來切換系統，不僅效能最佳、最不易死當，也是嵌入式工程師最踏實、最高效的智慧！
